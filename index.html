Hands-on lab, about 3 hours

Claims and fraud:
from a Postgres table to an app

An auto insurer has 1,000 claims in a database and a fraud problem. You will land the data with Fivetran, model it on the dbt platform with dbt Wizard doing the heavy lifting, and ship a Streamlit app in Snowflake.

What you are building

Five layers, one data set, one governed definition of every number.

FivetranLands the claims table in Snowflake in minutes.
SnowflakeStores it, runs everything, hosts the app.
dbt platformStaging, marts, contracts, tests, docs, jobs.
dbt WizardFixes what is broken, writes what is missing, answers questions.
ConsumptionExplore Mode to ask, Streamlit in Snowflake to ship.
Your business question: where is the money going on auto claims, and where does confirmed fraud concentrate?
Your safety net, before anything elseIf staging is red, the cause is almost always source_schema in dbt_project.yml or a sync that has not finished. Check those first rather than losing ten minutes.

  1. Use the repo your instructor gave you (dbt-insurance-lab-hol in the dbt-Hands-on-Labs org, or a copy of it). Create a branch in the dbt IDE before you edit.
  2. The dbt project sits at the repo root, so you will edit dbt_project.yml and the models directly.

0:08Fivetran: connect Postgres and start the sync14 min▸

Build a PostgreSQL to Snowflake connector. The point is not that configuring a connector is hard. It is that it takes a few minutes and then raw tables exist in Snowflake.

  1. Destination first. The connector cannot be created until it has somewhere to land. In Fivetran go to Destinations and add Snowflake. Use the Key pair authentication option and take the host, database (the one ending in _LANDING), warehouse, role, user and private key from your lab credentials card. Run Save & Test and wait for every check to go green.
  2. Then the connection. Add a PostgreSQL connector pointing at that destination. Host, port, database, user and password are on your credentials card.
  3. Name the connection postgres. Fivetran builds the Snowflake schema from the connection name plus the source schema, so your data lands in POSTGRES_INSURANCE in your ..._LANDING database.
  4. On the schema screen, select the insurance schema. You will see claims and icp_records land; the lab models use claims.
  5. Save, test, and start the initial sync. Then move on while it runs. Nobody watches a progress bar.

When it finishes, check it in a Snowflake worksheet:

select count(*) from <your_database>_LANDING.postgres_insurance.claims;   -- expect 1000

select collision_type, count(*) from <your_database>_LANDING.postgres_insurance.claims
group by 1 order by 2 desc;                                                     -- look for the '?'
Notice_fivetran_synced is not in the source. Fivetran adds it, and it is how you answer "when did this row last change".
0:22dbt platform: connect, point at your data, first green build16 min▸
  1. Create your dbt platform project, connect Snowflake, and connect the repo.
  2. Set your development credentials before you open the Studio editor. Go to your profile, then Credentials, pick this project, and enter your Snowflake username and authentication (key pair or password, as on your credentials card) and a target schema of your own, for example dbt_<firstname>_<lastname>. Without this the editor will not run anything.
  3. Create two environments now: a development one, and a production deployment one. Two minutes here saves confusion later.

Before you edit anything, confirm the exact schema Fivetran created. In a Snowflake worksheet:

show schemas like '%INSURANCE' in database <your_database>_LANDING;

In the Studio editor, open dbt_project.yml and change one line to the name that query returned (the repo used to ship insurance, which does not exist in your database):

If show schemas returned a different name (for example because you named the connection something else), use that instead.

The source database is derived for you: your DEV target database with _DEV/_PROD swapped for _LANDING. Set the source_database var only if your data lives elsewhere.

Then in the command bar:

0:46dbt Wizard I: four things are broken, fix them32 min▸

The centre of the lab. Run the whole project:

dbt build

It does not go green. Four things in your project are deliberately broken, in three independent branches, so one failure does not hide the rest. Some only appear after you fix another.

The loop Run, read the failure, ask dbt Wizard, read the diff, accept, run again. Wizard is an agent, not autocomplete: it writes, you stay accountable.

Start with this one, and keep it open. It works for all four.

dbt Wizard: the debug loop 
This failed when I ran dbt build:

<paste the full error or the failing test name here>

Find the root cause. Look at the model that failed AND the models it selects from, and check column names against what the upstream model actually produces. Tell me what is wrong and why before you change anything. Then propose the smallest fix, and show me the diff before applying it.

Then match what you see to the right prompt. These do not give away the answer; they make Wizard find it.

If you see a SQL error about an invalid identifier:

dbt Wizard: compile error 
This model fails with an "invalid identifier" error. Open the model, then open stg_insurance_claims, and compare the column names the model selects with the column names staging actually outputs. Fix the mismatch and tell me which one was wrong.

If a test fails with rows returned:

dbt Wizard: failing test, is the model or the test wrong? 
This singular test returns rows: <test name>.

Do NOT change the test yet. First run dbt show on the model it checks and on the raw data, and tell me with evidence whether the model is producing the wrong number or the test is asking for the wrong thing. If the model is wrong, explain the business rule it breaks, fix it, and show me the diff. If the test is wrong, tell me why.

If a contract fails:

dbt Wizard: contract mismatch 
The enforced contract on this model fails. Compare the columns the model SQL produces with the columns the contract declares in the YAML, name and data type. Tell me which side is the one that should change, given what the rest of the project (the Semantic View, the metrics, the tests) already calls this column, and fix the mismatch.
Two of the four have a fix that turns the build green and is still wrong Loosening a test until it passes, or labelling a value with something plausible, are both ways to get a green build and a wrong table. Before you accept any diff, ask: does this make the data right, or only the build green? If you are not sure, ask Wizard to show you the rows before and after.
Done whendbt build exits green for the four broken things. One test may still report a warning: that is a real data problem (a policy that starts after its own claim) and a warning is the right severity for one row in a thousand.

1:25dbt Wizard II: build from intent, not just repair25 min▸

Repairing is half of what Wizard is for. Now use it to create things that do not exist yet. Three exercises, in order of value. Do the first for sure.

How to brief an agentName the model it should read, state the grain, name the layer, say what contract and tests you expect, and ask it to verify with dbt show before it tells you it is done. A prompt with those four things gets a different quality of answer from "make a fraud table".

Exercise 1: build a mart from a business question (15 min). Where does confirmed fraud concentrate?

dbt Wizard: generate a model 
Create a new mart model called ins_fraud_signals in models/marts, reading from ref('ins_claims').

Goal: show where confirmed fraud concentrates. One row per dimension and value, across these ten dimensions of ins_claims: incident_severity, incident_type, insured_hobbies, insured_occupation, auto_make, policy_state, police_report_available, authorities_contacted, claim_size_band, incident_time_of_day.

Columns: signal_key (dimension and value joined, the primary key), signal_dimension, signal_value, claim_count, fraud_claim_count, fraud_rate, and fraud_lift, which is the value's fraud rate divided by the overall fraud rate.

Only include values with at least 20 claims, because lift on a tiny group means nothing.

Follow the conventions of the other marts: materialized as a table, every column explicitly cast with cast(), no ::, an enforced contract with a data_type for every column, a unique and not_null test on signal_key, and descriptions on every column. Put the YAML in models/marts/_insurance__marts.yml.

When done, run dbt build --select ins_fraud_signals and use dbt show to list the ten rows with the highest fraud_lift. Tell me which three signals stand out and whether the rest look like noise.
  • Before you accept it, read the SQL. Did it stack the dimensions once, or write ten near-identical queries?
  • Check the contract has all seven columns, and that the 20-claim floor is really in the query.
  • Open the result. How many signals stand out, and how many are noise? Which of them would you hand to a fraud investigator, and which would you not price a policy on?

Exercise 2: document and test a model that has nothing (5 min). The intermediate models ship with no YAML at all.

dbt Wizard: docs and tests 
int_insurance_claim_enrichment has no YAML. Create models/intermediate/_insurance__intermediate.yml for it. Read the model SQL first, then write a description for the model and for every derived column (age band, policy tenure, claim size band, claim to premium multiple, time of day, vehicle age, confirmed fraud amount), using the thresholds actually in the SQL.

Add tests where they are meaningful: unique and not_null on claim_id, accepted_values on every banded column with exactly the values the CASE expression can produce, and a non-negative check on confirmed_fraud_amount. Use the arguments: form for test arguments. Then run dbt build --select int_insurance_claim_enrichment and tell me if any test fails.

Exercise 3: unit test business logic (5 min). A unit test checks the logic with hand-written rows, no warehouse data.

dbt Wizard: unit test 
Write a dbt unit test for int_insurance_claim_enrichment that checks the claim_size_band thresholds at their exact boundaries: 9999.99 and 10000.00, 49999.99 and 50000.00, 79999.99 and 80000.00. Mock ref('stg_insurance_claims') with inline rows, and only assert on claim_size_band. Add a second assertion on insured_age_band at 29, 30, 59 and 60. Run it with dbt test --select test_type:unit and tell me whether the boundaries behave the way the comments in the model say they should.
Done whenins_fraud_signals builds, its contract is enforced, and you can name the three strongest signals out loud.
1:50Semantic layer: the same metrics, defined two ways8 min▸

Open two files side by side:

  • models/marts/sv_ins_claims_fraud.sql: a Snowflake Semantic View, defined as a dbt model. Cortex Analyst reads it if you use the optional Snowflake-native path.
  • models/marts/_insurance__marts.yml, the metrics: block under ins_claims: the dbt Semantic Layer definitions, served through the dbt MCP Server.

The question to leave with is not "which is better". It is: where should the definition of fraud rate live, and who else needs to read it?

dbt Wizard: compare the two layers 
Compare the metrics in sv_ins_claims_fraud.sql with the metrics: block under ins_claims in _insurance__marts.yml. List every metric that exists in only one of them and explain why it cannot exist in the other. Then check that fraud_rate, fraud_cost_share and portfolio_claim_to_premium_multiple are defined identically in both, and tell me if any of them would return a different number.
Find the honest differenceOne metric exists in only one layer, because MetricFlow has no standard-deviation aggregation. Two layers, same business, not always the same set of numbers. Better to find that here than in a meeting.
1:58Ship to production: job, docs, dbt Catalog12 min▸
  1. Commit your work to a branch and merge it into the branch your production environment tracks, or point the production environment at your working branch for the lab.
  2. Create a job in your production environment running dbt build, with Generate docs on run switched on. Run it. Run it a second time: unchanged models are skipped by dbt State.
  3. Open Catalog from the top navigation. Click Explore Lineage and find ins_claims. Look at its Details: contracted: true is the contract you enforced, published as a fact anyone can look up.
  4. Look at the lineage downstream of the marts. You will see an exposure, ins_fraud_command_centre. It is the Streamlit app you build in a few minutes, already in the graph.
Checkpoint 2: the second hard gateThe production job must succeed and generate docs. The next sections read what it built. Without it Catalog is empty and the Columns tab is blank.
Explore Mode reads productionThe next step answers questions about production data, so the production job has to have succeeded first. It also reads through an analytics credential the instructor set up, which can only see the three marts.
Snowflake grantsA dbt build recreates tables and drops the grants on them. Ask the instructor to re-run the grants after your job, or Explore Mode and the Streamlit app will not be able to read the marts. This is the single most common "it worked a minute ago" in the next two sections.
Why this mattersdbt Catalog and the dbt MCP Server read the same metadata through the same Discovery API. Catalog shows it to a human; the MCP Server hands it to an agent. Good AI answers come from descriptions, tests, contracts and metric definitions, which is to say from the pull request, not the prompt.
2:10Ask your data with dbt Wizard Explore Mode12 min▸

You have just seen exactly what metadata exists. Now watch an agent use it, without leaving the dbt platform and without writing any SQL.

  1. Open the dbt Wizard home tab.
  2. Click the Agent mode button at the bottom left of the Wizard panel and choose Explore only. In this mode Wizard can query and explain data but cannot edit files or run builds.
  3. Ask a question. Name the time period, the grouping and the filter. Then ask a follow-up in the same conversation.
  4. Switch between Chart, Table and SQL. The SQL view shows the query or the governed metric behind the answer, and you can copy it.
Explore Mode: start here 
In January and February 2015, what is the fraud rate by incident severity?

Then follow up, and work through these. Pick any three and keep the SQL for the next step.

Explore Mode: follow-up 
Now break that out by policy state, and show me only Major Damage claims.
Explore Mode: the questions 
1. Which hobbies of the insured have the highest fraud rate in January and February 2015? Show the number of claims behind each rate.
2. How much did confirmed fraud cost us, and what share of total claimed is that?
3. What is the average claim amount by incident type?
4. Which policy state and coverage level has the highest claim to premium multiple?
5. What is the fraud rate when there is no police report compared with when there is one?
6. Compare the average and the median claim amount by claim size band.
Read the SQL, every timeThe answer is only as good as what sits behind it. For each question, open the SQL view and check one thing: did Wizard use a governed metric (fraud_rate, total_claimed) or write its own query against a table? A metric means the definition lives in a pull request. A hand-written query means you are trusting the prompt.
The governance beatAsk: "What is the postcode of the insured on claim 100?" and see what happens. The postcode and the incident address were left out of every mart on purpose, and Explore Mode only reads what its credential can read. Note whether it answers, and where the control actually sits: in the model, or in the grants.
Two more experimentsAsk for the "loss ratio" and see what Wizard calls the number. The data compares two months of claims with a year of premium, so values near 40 are normal and it is a claim to premium multiple. Then ask something no metric covers, for example fraud rate by vehicle model, and see whether Wizard tells you it left the governed metrics.
Optional, Snowflake-nativeIf your instructor set it up, you can ask the same questions in Snowflake Intelligence through the HOL_INS_ANALYST agent, which reads the Snowflake Semantic View. Compare the two answers for the same question.
2:22Build the Streamlit app in Snowflake23 min▸

The last layer. The same governed marts that fed the agent now feed a small app for a human. Nothing in it recomputes a definition.

  1. Snowsight, Projects, Streamlit, + Streamlit App.
  2. Title claims_fraud_command_centre. Choose the database and schema where your production job built the marts, and a warehouse.
  3. Delete the starter code. Paste in the contents of streamlit_app/streamlit_app.py from the repo. Press Run.
  4. If it says it cannot read ins_claims, fix the database and schema in the sidebar. No code change needed.
From Explore Mode to the appTake one answer you liked in the last step, open its SQL view and copy the query. You will paste it into the app as a new tile. Replace the table names with the helper the app already uses, table('ins_claims'), so it follows the sidebar's database and schema.

Check the numbers against what Explore Mode told you:

WhereWhat you should see
Overview tiles1,000 claims, a fraud rate of 24.7%
Fraud rate by severityOne severity far above the rest

Three surfaces, one numberThe fraud rate in this app, the fraud_rate metric in dbt, and the answer Explore Mode gave you should agree. If they do not, one of them is reading something it should not, or Explore wrote its own query instead of using the metric.

Your task: add one tile, chart or filter. Look for the TODO at the bottom of the file. The best source is an Explore answer: paste its SQL in as a new tile. Or use any AI assistant you like in the Streamlit editor. Give it the context:

Extend the app 
I have a Streamlit in Snowflake app that reads the dbt marts ins_claims, ins_policy_portfolio and ins_incident_profile. Read the existing code, then add a selectbox in the sidebar to filter by insured_age_band, and add it to the `conditions` list so every claim-level tile responds. Keep the plain SQL style and do not recompute any metric that already exists. Also add a tile for the share of claims where police_report_available is 'No' or 'Unknown'.

Stretch: close the loop from model to consumer. The app has a panel that appears the moment ins_fraud_signals exists. If your production job built it in step 7, check the Where fraud concentrates tab. If it is not there, your job is not building it or your grants are stale.

dbt Wizard: a new mart for the app 
Create a mart ins_claims_weekly from ref('ins_claims'): one row per week of incident_date (date_trunc('week')), with claim_count, total_claimed, fraud_claim_count and fraud_rate. Primary key is the week start date. Enforce a contract, add unique and not_null on the key, cast every column explicitly, and verify with dbt show. Then tell me what a week-by-week chart of a two month window can and cannot tell us.
2:45Wrap: pull request, and what you built10 min▸

Commit and open a pull request against your own fork. Do not merge: the point is that the change is reviewable, not that it ships. Read the diff as a reviewer would:

  • Four small fixes, each one a line or two, each one explainable in a sentence.
  • Three new things Wizard wrote: a mart, some documentation and tests, and a unit test.
  • A contract on every mart that says exactly what is allowed out.

The full loop, done: raw table in Postgres, landed by Fivetran, modelled and governed in dbt, catalogued, asked in English, and shipped as an app.

Take-homeWhich of the four fixes would you have caught without a test? Which would you have caught without Wizard? And what did you accept from Wizard that you could not have explained yourself?
