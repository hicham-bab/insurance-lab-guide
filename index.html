Hands-on lab, about 3 hours

Claims and fraud:
from a Postgres table to an app

An auto insurer has 1,000 claims in a database and a fraud problem. You will land the data with Fivetran, model it on the dbt platform with dbt Wizard doing the heavy lifting, and ship a Streamlit app in Snowflake.

FivetranSnowflakedbt platformdbt Wizarddbt Wizard Explore ModeStreamlit in Snowflake

What you are building

Five layers, one data set, one governed definition of every number.

FivetranLands the claims table in Snowflake in minutes.
SnowflakeStores it, runs everything, hosts the app.
dbt platformStaging, marts, contracts, tests, docs, jobs.
dbt WizardFixes what is broken, writes what is missing, answers questions.
ConsumptionExplore Mode to ask, Streamlit in Snowflake to ship.
Your business question: where is the money going on auto claims, and where does confirmed fraud concentrate?
Your safety net, before anything elseIf staging is red, the cause is almost always source_schema in dbt_project.yml or a sync that has not finished. Check those first rather than losing ten minutes.

This singular test returns rows: <test name>.

1:25dbt Wizard II: build from intent, not just repair25 min▸

Repairing is half of what Wizard is for. Now use it to create things that do not exist yet. Three exercises, in order of value. Do the first for sure.

How to brief an agentName the model it should read, state the grain, name the layer, say what contract and tests you expect, and ask it to verify with dbt show before it tells you it is done. A prompt with those four things gets a different quality of answer from "make a fraud table".

Exercise 1: build a mart from a business question (15 min). Where does confirmed fraud concentrate?

dbt Wizard: generate a model 
Create a new mart model called ins_fraud_signals in models/marts, reading from ref('ins_claims').

Goal: show where confirmed fraud concentrates. One row per dimension and value, across these ten dimensions of ins_claims: incident_severity, incident_type, insured_hobbies, insured_occupation, auto_make, policy_state, police_report_available, authorities_contacted, claim_size_band, incident_time_of_day.

Columns: signal_key (dimension and value joined, the primary key), signal_dimension, signal_value, claim_count, fraud_claim_count, fraud_rate, and fraud_lift, which is the value's fraud rate divided by the overall fraud rate.

Only include values with at least 20 claims, because lift on a tiny group means nothing.

Follow the conventions of the other marts: materialized as a table, every column explicitly cast with cast(), no ::, an enforced contract with a data_type for every column, a unique and not_null test on signal_key, and descriptions on every column. Put the YAML in models/marts/_insurance__marts.yml.

When done, run dbt build --select ins_fraud_signals and use dbt show to list the ten rows with the highest fraud_lift. Tell me which three signals stand out and whether the rest look like noise.
  • Before you accept it, read the SQL. Did it stack the dimensions once, or write ten near-identical queries?
  • Check the contract has all seven columns, and that the 20-claim floor is really in the query.
  • Open the result. How many signals stand out, and how many are noise? Which of them would you hand to a fraud investigator, and which would you not price a policy on?

Exercise 2: document and test a model that has nothing (5 min). The intermediate models ship with no YAML at all.

dbt Wizard: docs and tests 
int_insurance_claim_enrichment has no YAML. Create models/intermediate/_insurance__intermediate.yml for it. Read the model SQL first, then write a description for the model and for every derived column (age band, policy tenure, claim size band, claim to premium multiple, time of day, vehicle age, confirmed fraud amount), using the thresholds actually in the SQL.

Add tests where they are meaningful: unique and not_null on claim_id, accepted_values on every banded column with exactly the values the CASE expression can produce, and a non-negative check on confirmed_fraud_amount. Use the arguments: form for test arguments. Then run dbt build --select int_insurance_claim_enrichment and tell me if any test fails.

Exercise 3: unit test business logic (5 min). A unit test checks the logic with hand-written rows, no warehouse data.

dbt Wizard: unit test 
Write a dbt unit test for int_insurance_claim_enrichment that checks the claim_size_band thresholds at their exact boundaries: 9999.99 and 10000.00, 49999.99 and 50000.00, 79999.99 and 80000.00. Mock ref('stg_insurance_claims') with inline rows, and only assert on claim_size_band. Add a second assertion on insured_age_band at 29, 30, 59 and 60. Run it with dbt test --select test_type:unit and tell me whether the boundaries behave the way the comments in the model say they should.
Done whenins_fraud_signals builds, its contract is enforced, and you can name the three strongest signals out loud.

PrerequisiteYour instructor or account admin must have made dbt v2 and dbt State available for the lab. Do not start an account trial or change shared environments or jobs. If either option is missing below, ask the instructor.

A. Switch your own Studio to dbt v2 and enable State

  2. In User development settings, set the dbt version dropdown to v2 Stable (the UI may also label it Preview, or formerly Fusion Stable). Click Save and Restart and wait for Status: Compiled.

dbt ls --select +ins_claims --resource-type model --output json --output-keys unique_id name database schema alias resource_type

C. Change a claims-routing threshold, then restore it

Take a baseline of the size-band mix first:

dbt show --inline "select claim_size_band, count(*) as claims, sum(total_claim_amount) as amount from {{ ref('ins_claims') }} group by 1 order by 2 desc" --limit 10
  1. Open models/intermediate/int_insurance_claim_enrichment.sql. Save the original line somewhere:

  5. Restore the exact original line, save, and run the build once more. Run the size-band query a last time and confirm you are back to your baseline.

Read the evidence carefullyViews expose upstream data dynamically, so a downstream view can show changed values even if State reuses its unchanged definition. This exercise shows a code change on a static dataset, not live source-freshness detection.
